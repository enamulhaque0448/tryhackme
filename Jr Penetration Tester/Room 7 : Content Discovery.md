# Web Content Discovery: Open Source & Conventional Files

When performing content discovery during a security assessment, web servers often expose specific, standardized files by convention. These files are designed for web crawlers, search engines, or performance optimization, but they frequently leak hidden architecture, staging sites, and sensitive directories.

---

## 🤖 1. robots.txt

The `robots.txt` file implements the **Robots Exclusion Protocol**. It tells legitimate search engine crawlers (like Googlebot) which parts of a website they should or should not index. 

### 🔍 Security Risk
Because site administrators must explicitly list sensitive directories to prevent them from appearing in public search engine results, `robots.txt` often serves as a "ready-made map" of interesting folders for penetration testers.

> ⚠️ **Note:** `robots.txt` is an advisory guideline for well-behaved bots. It is **not** a security mechanism. Any user can access restricted paths directly in their browser.

### 📝 Realistic Examples

#### Standard Disallow List Leaks
```text
User-agent: *
Allow: /
Disallow: /staff-portal/            # Leaks administrative portal
Disallow: /backup_old/              # Leaks deprecated data
Disallow: /staging/                 # Leaks development environment
Disallow: /wp-admin/                # Discloses the CMS backend framework (WordPress)
```

#### Multi-Bot Targeted Rules
Attackers inspect targeted sections to see what specific crawlers are blocked from seeing, which often hints at the nature of the application data:
```text
User-agent: Googlebot
Disallow: /private/analytics/

User-agent: Bingbot
Disallow: /financial-reports/
```

---

## 🗺️ 2. sitemap.xml

While `robots.txt` acts as a restriction map, `sitemap.xml` acts as an **inclusion map**. It explicitly lists the URLs that the site owner wants search engines to find and index cleanly.

### 🔍 Security Risk
Sitemaps automatically generated by Content Management Systems (CMS) or CI/CD pipelines often capture legacy, unlinked, or testing endpoints that developers forgot to purge. They also explicitly map out application query parameters.

### 📝 Realistic Examples

#### Standard XML Sitemap
```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://sitemaps.org">
   <url>
      <loc>http://target.local</loc>
      <lastmod>2026-08-14</lastmod>
   </url>
   <!-- Vulnerability Indicator: Parameterized endpoints -->
   <url>
      <loc>http://target.local/article?id=1</loc>
   </url>
   <!-- High Value Target: Leaked administrative/staging sections -->
   <url>
      <loc>http://target.local</loc>
   </url>
</urlset>
```

---

## 🚀 3. Additional Key Conventional Files (Must-Check)

To maximize your initial reconnaissance phase, always check for these additional conventional files that behave exactly like `robots.txt` and `sitemap.xml`.

### A. Security Contact Metadata (`security.txt`)
Defined by **RFC 9116**, this file resides at `/.well-known/security.txt` or `/security.txt`. It tells security researchers how to responsibly report vulnerabilities. 

* **Why it matters:** It can reveal pgp keys, target scopes, and internal communication channels.
* **Example:**
  ```text
  Contact: mailto:security@acme-it.local
  Expires: 2027-12-31T23:59:59.000Z
  Encryption: https://acme-it.local
  Policy: https://acme-it.local
  ```

### B. Human Credits (`humans.txt`)
A convention used by teams to give credit to authors, developers, and designers. It usually lives at `/humans.txt`.
* **Why it matters:** It triggers **OSINT (Open Source Intelligence)** leaks by naming exact developers, technologies, frameworks, and software stacks used to build the application.
* **Example:**
  ```text
  /* TEAM */
  Lead Developer: John Doe (johndoe@acme-it.local)
  Twitter: @JohnDoeDev

  /* SITE */
  Standards: HTML5, CSS3
  Components: jQuery v3.6.0, Bootstrap 5
  Software: Node.js, Express
  ```

### C. Web App Manifest (`manifest.json`)
Used in Progressive Web Apps (PWAs) to dictate how the app looks when installed on mobile devices. Typically found at `/manifest.json` or linked in the HTML source header.
* **Why it matters:** Discloses underlying API scopes, application start URLs, and system orientation layouts.
* **Example:**
  ```json
  {
    "short_name": "AcmePortal",
    "name": "Acme IT Support Staff Portal",
    "start_url": "/staff-portal/dashboard.html?platform=pwa",
    "background_color": "#ffffff",
    "display": "standalone"
  }
  ```

---

## 🛠️ 4. Defensive Best Practices (Remediation)

If you are hardening a web application against discovery techniques, apply these rules:

1. **Do Not Rely on Security Through Obscurity:** Never use `robots.txt` to "hide" sensitive portals. If an asset is private, secure it with robust authentication and access control mechanisms (IP whitelisting, MFA).
2. **Dynamic Sitemap Generation:** Filter out administrative paths, staging domains, and API endpoints from public-facing `sitemap.xml` files.
3. **Proper HTTP Status Codes:** Ensure that pages dropped or removed from production throw a true `404 Not Found` or `410 Gone` error, rather than redirecting to a page that crawlers can catalog.

# OSINT: Advanced Search Engines & Google Dorking

Google Hacking—commonly known as **Google Dorking**—is an Open-Source Intelligence (OSINT) technique that uses advanced search engine operators to locate information that a target website has accidentally exposed to the public internet.

This is a form of **Passive Reconnaissance**. Because you are querying Google's cached index database rather than interacting directly with the target infrastructure, the target organization cannot log or detect your activity.

---

## 🛠️ Complete Advanced Search Operator Reference

While core operators filter domains and extensions, combining advanced modifiers isolates severe configuration flaws instantly.

| Operator | Syntax Example | Tactical Vulnerability Discovered |
| :--- | :--- | :--- |
| **`site`** | `site:target.com` | Restricts results strictly to the target domain scope. |
| **`inurl`** | `inurl:admin` | Finds specific words hidden anywhere inside the URI string path. |
| **`filetype`** / **`ext`** | `filetype:log` | Filters by precise file extensions (configuration files, backups). |
| **`intitle`** | `intitle:"index of"` | Finds specific phrases in the browser tab title (indicates open directories). |
| **`intext`** | `intext:"SQL syntax"` | Finds sensitive terms, error logs, or leaks in the page body text. |
| **`cache`** | `cache:target.com` | Pulls up historical, cached versions of a page, even if the live page was taken offline. |
| **`link`** | `link:target.com` | Lists external websites that are linking back to your target. |

---

## 🔀 Powerful Combined Dorking Formula Patterns

Real-world penetration testing relies on chaining these operators together to find specific weaknesses.

### 1. Uncovering Exposed Directory Listings
When a web server is misconfigured to allow directory browsing, it exposes files in an "Index of" format. You can hunt for these folders across your target site using:
```text
site:target.com intitle:"Index of"
```
*To drill down further for specific folders like backups or emails:*
```text
site:target.com intitle:"Index of" inurl:backup
site:target.com intitle:"Index of" intext:id_rsa
```

### 2. Hunting for Leaked Passwords and Database Credentials
Developers occasionally leave backup configurations, configuration keys, or environment settings open to indexing.
```text
site:target.com filetype:env DB_PASSWORD
site:target.com filetype:ini "database" intext:password
site:target.com filetype:log intext:"password connection failed"
```

### 3. Locating Exposed Administrative & Authentication Interfaces
Finding unlinked portal entrance portals can expose your target to brute-force or injection attacks.
```text
site:target.com inurl:login intitle:admin
site:target.com (inurl:dashboard | inurl:portal) intitle:internal
```

### 4. Isolating Document and Metadata Leaks
Corporate portals leak information through forgotten internal manuals, server setup instructions, or network topology drawings.
```text
site:target.com (filetype:pdf | filetype:doc | filetype:xlsx) intext:"internal use only"
```

---

## 🗃️ The Google Hacking Database (GHDB)

You do not need to memorize every single query pattern. The security community catalogs active, dangerous Google search strings in a centralized public clearinghouse.

*   **Resource:** Managed by Exploit-DB, the **Google Hacking Database (GHDB)** maps out thousands of active dorks categorized by intent.
*   **Categories Available**:
    *   Vulnerable Servers
    *   Error Messages containing sensitive data
    *   Files containing passwords
    *   Sensitive Directories

---

## 🛡️ Remediation and Defense

If you are defending your enterprise application against Google Dorking attacks, ensure you enforce these parameters:

1.  **Configure `robots.txt` properly:** Use explicit `Disallow` rules to stop search bots from knocking on dev portals or file repositories.
2.  **Deploy `NOINDEX` Meta Tags:** Place `<meta name="robots" content="noindex, nofollow">` directly into the HTML headers of internal application pages.
3.  **Disable Directory Browsing:** Modify your server configuration blocks (`httpd.conf` or `nginx.conf`) to block general file indexing by defaulting directory hits to a strict `403 Forbidden` response code.
# OSINT: Repositories & Historical Archives

During the passive reconnaissance phase of an engagement, investigating historical archives, cloud storage, and public source repositories can expose architectural flaws, leaked credentials, or deprecated endpoints that are missing from the live production site.

---

## 🏛️ 1. The Wayback Machine (Internet Archive)

The Wayback Machine archives snapshots of the public internet over decades. It serves as a historical record of an organization's web assets.

### 🔍 Security Risk
Websites frequently evolve, but administrators regularly fail to scrub deprecated endpoints. By analyzing historical snapshots, security teams can discover **abandoned login screens, deprecated API endpoints, legacy directory structures**, or short-lived data exposures that developers quickly deleted but the archive caught.

### 🛠️ Practical Methodology & Tooling
Instead of manually navigating the web calendar GUI, penetration testers automate endpoint collection using command-line tools to build target parameter fuzz lists.

*   **Tool Highlight:** `waybackurls` or `gau` (Get All URLs)
*   **Command Example:**
    ```bash
    # Feed a domain to waybackurls to print all historical paths
    echo "target.com" | waybackurls > wayback_endpoints.txt
    
    # Filter for high-interest parameters, scripts, or configurations
    grep -E "\.(json|config|xml|php|bak|sql)" wayback_endpoints.txt
    ```

---

## 🐙 2. Public Code Repositories (GitHub, GitLab, Bitbucket)

Developers use version control systems like Git to manage software changes. When corporate projects or public employee accounts interact with platforms like GitHub, severe visibility issues can arise.

### 🔍 Security Risk
The primary risk stems from **hardcoded secrets**—such as private API tokens, database connection strings, SSH keys, or environment files (`.env`). Crucially, if a developer pushes a secret to a public repository and then fixes it by deleting the line in a *subsequent* commit, the secret remains completely accessible inside the project's **Git commit history**.

### 🛠️ Look in the History, Not Just the Code
When evaluating an organization's public code repository, attackers crawl the commit history logs (`git log` or structural diffs) rather than analyzing only the final branch output.

*   **Manual GitHub Dork Search Operations:**
    *   `org:TargetCompany "password"`
    *   `target.com "API_KEY"`
    *   `filename:.env`
*   **Automated Tooling (Secret Scanning):**
    ```bash
    # Use GitLeaks or TruffleHog to parse a repository history for entropy signatures
    gitleaks detect --repo-path=/path/to/cloned/repo -v
    ```

---

## 🪣 3. Cloud Storage Enumeration (Amazon S3 Buckets)

Amazon Simple Storage Service (S3) allows organizations to store files and web assets in logical containers called **buckets**.

### 🔍 Security Risk
While AWS handles infrastructure security, identity configuration lies with the user. Misconfigured buckets often inherit broad public access privileges, leaving files vulnerable to unauthorized listing and download operations. This can expose **backup archives, user data sheets, source files, or internal code modules**.

### 🔗 Standard S3 URL Layout Syntax
An organization's S3 deployment follows predictable naming schemas:
*   `https://[bucket-name].s3.amazonaws.com`
*   `https://amazonaws.com[bucket-name]`

### 🧪 Practical Naming and Testing Patterns
Attackers combine variations of the target's corporate name with common asset keywords to search for hidden repositories:

| Target Structure Type | Fuzz Wordlist Examples |
| :--- | :--- |
| **Assets & Content** | `target-assets`, `target-images`, `target-www`, `target-media` |
| **Backups & Code** | `target-backup`, `target-db`, `target-sql`, `target-source`, `target-dev` |
| **Internal Ops** | `target-internal`, `target-hr`, `target-logs`, `target-finance` |

*   **Testing Access via the AWS CLI:**
    ```bash
    # Attempt to read a bucket's root directory listing anonymously
    aws s3 ls s3://target-backup --no-sign-request
    ```

---

## 🛡️ Remediation and Defense

To mitigate risks within historical databases, public repositories, and storage buckets:

1.  **Enforce Secret Scanning in CI/CD:** Deploy pre-commit hooks (like `pre-commit` or native GitHub advanced security alerts) to stop API keys or `.env` files from ever entering a Git repository.
2.  **Purge History Completely:** If a secret is committed, do not simply delete the text file line. Use tools like `git-filter-repo` or BFG Repo-Cleaner to completely purge the asset from the historical Git database tree, and **immediately rotate the compromised credential**.
3.  **Implement AWS S3 Block Public Access:** Enable the account-level "Block Public Access" setting within AWS to prevent any buckets from accidentally exposing directories. Use Identity and Access Management (IAM) policies to enforce explicit authentication parameters.
4.  **Request Wayback Removal:** If sensitive information is exposed on a historical archive snapshot, submit an official URL removal request to the Internet Archive team to remove the cached files from public visibility.

# Automated Content Discovery: Gobuster Fundamentals

While manual checks and OSINT provide a solid foundation, finding unlinked web files or hidden routes requires automation. Automated content discovery uses directory brute-forcing tools to rapidly send thousands of HTTP requests using structured **wordlists** to identify hidden folders, files, and resources.

---

## 🏎️ Introducing Gobuster

**Gobuster** is a high-performance, open-source automation tool written in Go. Because it leverages Go's concurrency model, it is significantly faster than legacy interpreted scripts (like DirBuster or original Dirb) and is a staple tool in Kali Linux and pentesting environments.

Gobuster operates in multiple modules:
*   **`dir`**: Brute-forcing files and directories on a web server.
*   **`dns`**: Enumerating subdomains.
*   **`vhost`**: Finding virtual hosts hosted on a single IP.

---

## 🗂️ The Importance of Wordlists (SecLists)

An automated scan is only as effective as the wordlist powering it. If a hidden directory is named `/s3cr3t-portal` and it is not in your text file, Gobuster will never find it.

The industry-standard repository for reconnaissance lists is **SecLists**. On standard security platforms (like the TryHackMe AttackBox or Kali Linux), it is located at:
```text
/usr/share/wordlists/SecLists/
```

### Essential Web Content Wordlists
When performing directory discovery, look for these specific paths inside SecLists:
*   `Discovery/Web-Content/common.txt` – Excellent for low-footprint, rapid baseline checks.
*   `Discovery/Web-Content/directory-list-2.3-medium.txt` – A massive, highly effective list based on real-world scraped web directory strings.

---

## 🛠️ The `dir` Mode: Core Syntax & Practical Use

The `dir` module attempts to append every word from your chosen wordlist to the end of your target URL to see how the server responds.

### 1. Basic Directory Scanning
Both the target URL (`-u`) and the wordlist path (`-w`) are strictly mandatory fields.
```bash
gobuster dir -u "http://10.48.180.24" -w /usr/share/wordlists/SecLists/Discovery/Web-Content/common.txt
```

### 2. Advanced Enumeration (Filtering Extensions & Status Codes)
By default, web servers serve files with extensions like `.php`, `.html`, or `.json`. You can instruct Gobuster to test for explicit file variations simultaneously using the `-x` flag.

```bash
gobuster dir -u "http://10.48.180.24" \
             -w /usr/share/wordlists/SecLists/Discovery/Web-Content/common.txt \
             -x .php,.txt,.html,.js \
             -s 200,301 \
             -t 50 \
             -o gobuster-results.txt
```

### 📋 Key Technical Flags Broken Down

| Flag | Long Flag | Practical Purpose |
| :--- | :--- | :--- |
| **`-t`** | `--threads` | Alters processing speed by increasing concurrent requests (Default is `10`). Maximize to `50` or `100` for labs; minimize for fragile production environments. |
| **`-x`** | `--extensions` | Appends extensions to words (e.g., if word is `admin`, it checks `admin.php`, `admin.txt`). |
| **`-s`** | `--status-codes` | Filters out noise. Only prints responses matching specific status codes (e.g., successful or moved). |
| **`-o`** | `--output` | Saves output straight to a file. Essential for logging evidence for a final report. |
| **`-r`** | `--followredirect` | Tells Gobuster to follow `301/302` redirects to find out where they lead rather than dropping the link. |
| **`-k`** | `--no-tls-validation` | Bypasses self-signed or invalid HTTPS SSL/TLS certificate warnings in lab networks. |
| **`--delay`** | *(N/A)* | Introduces a pause between requests (e.g., `--delay 500ms`) to evade rate-limiting firewalls. |

---

When Gobuster runs, its terminal output displays the discovered path, the raw HTTP status code, and the response file size in bytes:

<img width="1476" height="533" alt="image" src="https://github.com/user-attachments/assets/4f3a8ab7-0c4c-4501-ae6a-94cd676a52a6" />


### 🧠 HTTP Status Code Security Reference Cheat Sheet
*   **`200 OK`**: The resource exists and is fully accessible. Immediately navigate to this endpoint in your browser.
*   **`301 Moved Permanently / 302 Found`**: The server redirects traffic somewhere else. This usually indicates a true directory path folder. Use the `-r` flag to track where it drops you.
*   **`403 Forbidden`**: The resource or directory exists on the system, but you do not have permission to view it. This is a massive clue—it indicates an asset is hidden behind authentication or IP constraints.
*   **`404 Not Found`**: The asset does not exist. (Gobuster hides these automatically to avoid filling your screen with thousands of errors).

---

## 🛡️ Defending Against Automated Scans

From a defensive perspective, automated directory brute-forcing leaves a massive footprint in server infrastructure log files. 

1.  **Rate Limiting & WAFs**: Deploy a Web Application Firewall (WAF) or tools like `Fail2ban` to monitor inbound connection frequencies. If a single IP makes 5,000 requests in 30 seconds, drop their traffic immediately.
2.  **Custom 404 Pages**: Ensure your server is not leaking backend system structural specs via the default error page formatting.
3.  **Honeypots**: Create artificial directories (like `/admin-backup/`) that aren't used by the site but are common in wordlists. If an IP requests that path, automatically flag it as a hostile scanner and trigger an incident alert.
# Automated Infrastructure Mapping: Subdomains & Virtual Hosts

When broadening an application's attack surface, mapping out hidden assets or alternate routing pathways is essential. Software patched or hardened on a core domain (e.g., `target.thm`) may be left outdated, misconfigured, or entirely exposed on an alternative endpoint or internal staging portal (e.g., `dev.target.thm`). 

---

## 🔍 Subdomains vs. Virtual Hosts (Vhosts)

Before executing automated discovery tools, it is crucial to understand how these routing methodologies differ technically:

| Feature | Subdomain (`dns` Mode) | Virtual Host (`vhost` Mode) |
| :--- | :--- | :--- |
| **Resolution Layer** | **Network Layer (DNS Server)** | **Application Layer (Web Server)** |
| **How it Works** | A DNS request is sent asking the network infrastructure for an IP mapping (e.g., `A` record for `blog.target.thm`). | An HTTP request is sent to an IP, but the `Host:` request header indicates which specific site file root to serve. |
| **Visibility** | Publicly discoverable by querying authoritative network nameservers. | Often hidden entirely inside internal web servers (Apache/Nginx configuration blocks) without explicit DNS entries. |

---

## ⚙️ Environment Preparation: Local Lab Routing

In lab environments (like TryHackMe) where external authoritative DNS servers do not index target resources, you must configure local resolution components on your testing machine (AttackBox/Kali) before executing tool suites.

### Step 1: Force Custom Nameserver Configuration
To route active DNS network lookup queries through the target's internal DNS manager portal, modify the `dnsmasq` system file:

1. Open the file in an interactive terminal text editor:
   ```bash
   sudo nano /etc/resolv-dnsmasq
   ```
2. Insert the target network IP address as the absolute primary priority line:
   ```text
   nameserver 10.48.180.24
   nameserver 169.254.169.253
   ```
3. Save (`Ctrl+O` -> `Enter`) and exit (`Ctrl+X`).
4. Restart the networking service daemon to flush configurations into memory:
   ```bash
   sudo systemctl restart dnsmasq   # Or: /etc/init.d/dnsmasq restart
   ```

### Step 2: Manually Map the Core Host Record
To bypass broad internet domain lookups for custom top-level testing domains (like `.thm`), inject a static mapping directly into your machine's system host table file:

1. Open the system hosts layout configuration:
   ```bash
   sudo nano /etc/hosts
   ```
2. Append the target layout signature rule at the very bottom:
   ```text
   10.48.180.24 example.thm
   ```
3. Save, exit, and verify active network connectivity by using a standard ping echo:
   ```bash
   ping -c 3 example.thm
   ```

## 🛠️ 1. Gobuster DNS Mode (Subdomain Brute-Forcing)

The `dns` module conducts targeted lookups against a network nameserver by matching a selected wordlist array directly against a parent top-level domain scope.

### Core Command Syntax
```bash
gobuster dns -d example.thm \
             -w /usr/share/wordlists/SecLists/Discovery/DNS/subdomains-top1million-5000.txt \
             --wildcard \
             -i
```
<img width="1664" height="598" alt="image" src="https://github.com/user-attachments/assets/2d205481-c488-43a2-ac74-470f71915396" />


### 📋 Key DNS Flag Attributes Explained
*   **`-d` / `--domain`**: The master parent base domain you want to probe against.
*   **`-i` / `--show-ips`**: Instructs the terminal window to print out the resolved IP mapping target next to discovered items.
*   **`-r` / `--resolver`**: Directs Gobuster to drop default configurations and leverage a designated IP as the custom DNS server for lookups.
*   **`--wildcard`**: Enforces ongoing scanning sequences even if a wildcard record exists. Wildcard setups redirect *all* non-existent subdomains to a single lander IP, which causes standard scanners to report thousands of false-positive entries.

---

## 🛠️ 2. Gobuster VHOST Mode (Virtual Host Fuzzing)

The `vhost` module evaluates web applications at the application layer. It interacts directly with the target server IP address, iterating through names inside a wordlist file and inserting them dynamically into the HTTP **`Host:` header field** to capture unique server directory responses.

### Core Command Syntax
```bash
gobuster vhost -u "http://10.48.180.24" \
               --domain example.thm \
               -w /usr/share/wordlists/SecLists/Discovery/DNS/subdomains-top1million-5000.txt \
               --append-domain \
               --exclude-length 250-320
```
<img width="1894" height="479" alt="image" src="https://github.com/user-attachments/assets/c828c718-3098-4cd8-9f90-1077fe74fdf9" />


### 📋 Key VHOST Flag Attributes Explained
*   **`-u` / `--url`**: The physical target base IP address or base URL where the web application server is reachable.
*   **`--append-domain`**: Tells Gobuster to automatically structure wordlist names into proper FQDN syntax (e.g., if checking the word `shop`, it formats the HTTP request header as `Host: shop.example.thm`).
*   **`--exclude-length`**: Filters out noise. If a web server responds to non-existent virtual hosts with a standard error page, that page will always have an identical content byte count. Excluding that specific character length automatically screens out false positives.

---

## 🛡️ Remediation and Defensive Countermeasures

To protect network assets against unauthorized topology mapping and infrastructure tracking:

1.  **Disable Zone Transfers (AXFR)**: Ensure nameservers are configured to drop requests for full database configuration layouts unless explicitly authorized by specific secondary backup server IPs.
2.  **Audit Web Server Configuration Overlays**: In Apache or Nginx architectures, drop requests targeting fallback virtual hosts or default fallback document root pathways by explicitly dropping unmatched host vectors with a strict `444 No Response` or `403 Forbidden` response header code.
3.  **Sanitize Development Environments**: Do not associate development, staging, or alpha-test internal nodes with publicly resolvable corporate nameserver records.
